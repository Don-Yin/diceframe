# DiceFrame 文档受众边界与公开清理计划

状态：待确认计划；本文件只记录后续清理范围，不改变当前文档树。

## 目标

让公开仓库中的文档能明确区分三类受众：

1. 玩家：知道如何安装、创建游戏、游玩和排错；
2. 公开开发者/内容作者：知道稳定的扩展契约、内容格式和架构边界；
3. 维护者：保存未发布方案、施工顺序、迁移草案和内部安全实现。

玩家文档不应出现分支名、未发布 schema、内部 PR 顺序或 Agent 授权实现细节。公开开发者文档也不应把本地工作区实现描述成已发布契约。

## 当前发现

需要后续处理的主要区域：

- `docs/design/`：包含本地未合并实现、维护者提案和 Agent 内部协议；
- `docs/plans/`：包含产品路线、PR 拆分和未实现方案；
- `docs/GAL_TRACK_PLAN.md` 与 `docs/CONTENT_ARCHITECTURE_VNEXT_MASTER_PLAN.md`：内部施工计划和重构母方案；
- 未发布或本地实现 ADR：0007、0008、0009、资源恢复 ADR、0011；
- `docs/LOREBOOK_MIGRATION.md`：维护者迁移笔记，不是玩家指南；
- `docs/en/updates.md` 与 `docs/zh/updates.md`：部分段落暴露本地 schema 变体和内部 reader fence，可改写为用户可执行的升级说明。

稳定的用户指南、扩展契约、内容包格式、Lorebook adapter、规则来源映射和历史归档暂不在本计划中删除。

## 分阶段方案

### 阶段一：建立标记和索引边界

- 为文档补充统一的 `audience` 与 `status` 约定：`player`、`developer`、`maintainer`；`current`、`proposed`、`historical`。
- 修改 `docs/README.md`，把维护者材料从 Current Contracts 和玩家入口中分开。
- 修改 `docs/adr/README.md`，分离已发布 ADR、未发布 ADR，并修复重复的 ADR 编号。
- 检查所有相对链接，不能让公开文档指向已下线的内部文件。

### 阶段二：隔离或下线内部材料

- 维护者仍需保留的方案迁移到私有规划区或单独的内部归档，不进入默认公开文档导航。
- 纯内部施工稿、分支交接稿和未发布 Agent 协议从公开仓库当前树移除；Git 历史保留可追溯性。
- 历史归档保留时明确标注为 historical，不让它参与当前功能说明。

### 阶段三：清理公开手册

- 将升级说明中的内部 schema、分支和 reader fence 改成玩家可执行的备份、兼容性和失败恢复说明。
- 将 Agent 公开说明限制在用户能使用的行为、确认流程和隐私边界；内部 registry、receipt、token budget 和恢复实现放到维护者材料。
- 中英文用户文档保持语义一致，并与 `diceframe-content` 的公共手册边界对齐。

## 验收标准

- 玩家从 `docs/README.md` 进入时只会看到用户指南和稳定的公开契约。
- 普通开发者不会被未发布分支、PR 序列或本地 schema 误导。
- 维护者文档仍可从私有规划区或 Git 历史恢复。
- 全部公开 Markdown 相对链接有效；不包含凭据、个人路径、运行时数据或本地草稿。
- 这项清理不改变产品代码、存档格式、API 或运行时行为。

## 本阶段不做的事

- 不删除 Git 历史，不重写公开仓库历史；
- 不在本 PR 中移动或删除现有内部文档；
- 不把提案内容写成已发布功能；
- 不修改用户指南的产品行为，除非后续阶段有对应实现证据。
